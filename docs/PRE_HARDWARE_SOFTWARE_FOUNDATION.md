# 接硬件前的软件基础设计

本文规定 ESP32-S3 机器人控制器在连接实际 PCB 前应完成的软件基础。硬件连接和引脚以
[`hardware/schematics/robot_controller_2026-07-31.svg`](../hardware/schematics/robot_controller_2026-07-31.svg)
为准；架构参考 [`reference/legacy_embedded`](../reference/legacy_embedded) 精选旧工程的模块化、
诊断和安全设计，但不照搬其 ESP32 + STM32 + 五体节拓扑。

## 1. 阶段目标

接板前要达到的不是“所有机器人算法完成”，而是建立一个安全、可测试、以后不用推倒重写的底座：

- 任意模块失败都不会让电机或舵机意外动作。
- 网络、串口和未来的手柄命令进入同一条控制链路。
- 驱动层不依赖 HTTP、GUI 或具体运动算法。
- 所有外部输入都经过范围检查、超时检查和状态机授权。
- 没有 PCB 时也能通过编译、主机单元测试和协议测试发现大部分软件错误。
- 接板后只需逐层验证驱动，不需要边上电边重构架构。

本阶段不实现完整姿态融合、复杂自动驾驶、强化学习、OTA、多体节同步和最终运动参数调优。

## 2. 当前硬件与软件边界

当前 ESP32-S3 直接连接：

| 模块 | 引脚 | 软件职责 |
|---|---|---|
| DRV8833 nSLEEP | GPIO3 | 驱动器总使能，低电平休眠 |
| DRV8833 nFAULT | GPIO4 | 故障输入，低有效 |
| Motor A | GPIO46/GPIO9 | 两路 PWM 控制方向与占空比 |
| Motor B | GPIO5/GPIO6 | 两路 PWM 控制方向与占空比 |
| 舵机 PWM | GPIO45 | 50 Hz PWM |
| MPU6050 INT | GPIO8 | DATA_READY 中断输入 |
| MPU6050 I2C | GPIO11/GPIO12 | SCL/SDA，地址 0x68 |
| 外部低有效接口 | GPIO35 | 经 2N7002 将外部接口拉低 |

旧工程中的 STM32、Fashion Star 串口舵机总线、PC0-PC3 四路 ADC 和五块 ESP32 节点不属于当前板子的驱动层。

## 3. 目标软件分层

```text
上位机 / 浏览器 / Xbox
          |
    HTTP / 可选兼容协议
          |
      command_router
          |
      control_manager
   _______|________________
  |       |        |       |
motor   servo    power    safety
  |       |        |       |
DRV8833  LEDC     GPIO   fault/watchdog

MPU6050 -> sensor_manager -> status_snapshot -> HTTP/日志
配置参数 -> config_store(NVS) -----------^
```

### 3.1 `board_pins`

- 只保存板级引脚、总线编号和不会运行时变化的硬件常量。
- 业务代码禁止直接写 `GPIO_NUM_x`。
- 原理图引脚改变时，只需要集中修改这里并重新跑验证。

### 3.2 驱动层

- `drv8833`：只负责初始化、休眠、Motor A/B 输出、nFAULT 读取和硬件停止。
- `servo_pwm`：只负责 PWM、脉宽换算和输出开关。
- `mpu6050`：只负责寄存器配置、读取原始数据和设备级错误。
- `power_control`：只负责 GPIO35 对 2N7002 的安全控制。
- 驱动层不得启动 Wi-Fi、解析 JSON、保存全局运动状态或调用 GUI 语义。

### 3.3 控制层

新增 `control_manager`，成为执行器的唯一调用者：

- 接收已经校验过的命令。
- 检查系统状态是否允许执行。
- 进行电机混控、斜坡、换向保护和舵机速率限制。
- 更新统一状态快照。
- 处理停止、急停、看门狗和硬件故障。

HTTP 回调、串口解析器和未来 Xbox 接口都不能直接调用电机或舵机驱动。

### 3.4 服务层

- `command_router`：统一命令结构、参数校验、序列号和来源标记。
- `wifi_control`：网络连接、HTTP 路由和响应，不负责运动计算。
- `sensor_manager`：固定频率读取 IMU，执行换算、校准和健康检查。
- `status_snapshot`：提供线程安全的只读系统状态。
- `config_store`：管理 NVS 参数、版本、默认值和合法范围。

## 4. 安全启动顺序

原始程序曾在启动后使能 DRV8833 并把舵机置于 90°；当前 P0 实现已经按以下安全顺序完成整改：

1. 第一时间将 GPIO35 输出锁存为低，保持 2N7002 关闭、外部接口释放。
2. 将 DRV8833 nSLEEP 拉低，四路电机 PWM 为 0。
3. 舵机 PWM 暂不输出，不能在启动时自动转到 90°。
4. 初始化日志、NVS 和复位原因记录。
5. 初始化驱动，但仍保持所有执行器禁止状态。
6. 检查配置版本与范围；非法配置回退到安全默认值。
7. 初始化 I2C 和 MPU6050。IMU 失败可以进入降级模式，但必须上报。
8. 初始化 Wi-Fi、HTTP、命令队列和任务。
9. 完成自检后进入 `SAFE`，等待显式 ARM 命令。
10. 只有 `ARM` 成功后进入 `READY`；收到有效运动命令后进入 `RUNNING`。

任何初始化步骤失败时，不得调用“恢复到上次速度”或自动移动舵机。

## 5. 系统状态机

### 5.1 状态

| 状态 | 含义 | 执行器行为 |
|---|---|---|
| `BOOT` | 启动初始化 | 电机休眠、舵机无输出、GPIO35 释放 |
| `SAFE` | 初始化完成但未解锁 | 拒绝运动命令，允许查询和诊断 |
| `READY` | 已解锁、等待命令 | 电机为 0，舵机仍保持安全策略 |
| `RUNNING` | 正在执行有效命令 | 接受刷新命令并启用超时保护 |
| `FAULT` | 硬件或软件故障锁存 | 立即停车、DRV8833 休眠、拒绝运动 |
| `ESTOP` | 用户急停锁存 | 与 FAULT 同样禁止执行器，需显式清除 |

### 5.2 关键转换

- `BOOT -> SAFE`：基础初始化完成，无不可恢复错误。
- `SAFE -> READY`：收到明确 ARM 命令且 nFAULT 正常。
- `READY -> RUNNING`：收到合法的非零运动命令。
- `RUNNING -> READY`：正常停止或速度回到零。
- 任意状态 `-> FAULT`：nFAULT、驱动调用失败、控制任务异常或内部一致性错误。
- 任意可运行状态 `-> ESTOP`：用户急停、控制通信超时或上位机断开策略触发。
- `FAULT/ESTOP -> SAFE`：只能在执行器已停止后，由显式 CLEAR 命令触发；硬件故障仍存在时不得清除。

急停优先级高于所有普通命令，不能被队列中较早的运动命令覆盖。

## 6. 统一命令模型

所有入口转换为同一个内部结构：

```c
typedef enum {
    ROBOT_CMD_ARM,
    ROBOT_CMD_DISARM,
    ROBOT_CMD_ESTOP,
    ROBOT_CMD_CLEAR_FAULT,
    ROBOT_CMD_DRIVE,
    ROBOT_CMD_MOTOR_DIRECT,
    ROBOT_CMD_SERVO,
    ROBOT_CMD_POWER_CONTROL,
} robot_command_type_t;

typedef struct {
    robot_command_type_t type;
    uint32_t sequence;
    int64_t received_at_us;
    command_source_t source;
    union {
        struct { int16_t throttle; int16_t steering; } drive;
        struct { int16_t motor_a; int16_t motor_b; } motors;
        struct { int16_t angle_deg; } servo;
        struct { bool asserted; } power;
    } value;
} robot_command_t;
```

要求：

- `throttle`、`steering`、`motor_a`、`motor_b` 均为 `-100..100`。
- 舵机角度先用 `0..180`，之后可由配置改变逻辑范围。
- 每条命令带接收时间；执行前丢弃超过有效期的运动命令。
- 每条命令带递增序列号，响应返回相同序列号。
- 网络、串口和兼容协议使用同一套校验函数。
- 队列满时优先保留 STOP/ESTOP，普通运动命令可以覆盖同来源的旧运动命令。

## 7. 电机控制基础

### 7.1 两种接口

1. 直接接口：分别给 Motor A、Motor B 设置 `-100..100`，用于板测。
2. 行驶接口：输入 `throttle` 和 `steering`，进行差速混控：

```text
motor_a = clamp(throttle + steering, -100, 100)
motor_b = clamp(throttle - steering, -100, 100)
```

如果真机方向相反，只通过配置中的 `invert_motor_a/b` 修正，不在业务代码散落负号。

### 7.2 输出保护

- 默认 PWM 频率沿用 16 kHz。
- 输出按固定周期渐变，建议初始斜率为每 10 ms 改变不超过 5%。
- 从正转切到反转时必须先降到 0，保持可配置死区，再反向加速。
- `speed=0` 使用滑行还是制动必须显式定义；第一版采用当前驱动的滑行停止。
- 非零运动命令必须周期刷新，建议超时 1 秒；后续真机可缩短到 300–500 ms。
- nFAULT 拉低时立即把四路 PWM 清零并拉低 nSLEEP。
- 控制层保存目标值、实际输出值、最后命令时间、故障次数和看门狗停车次数。

## 8. 舵机控制基础

- 启动时不主动输出 90°，避免舵机突然运动。
- 第一次 ARM 后仍不移动，只有显式舵机命令才开始 PWM。
- 默认脉宽暂定 500–2500 µs、50 Hz，但必须由真机规格确认。
- 配置项包括中位角、最小角、最大角、最小/最大脉宽、方向反转和最大变化速率。
- 所有命令先限幅，再按变化速率逐步接近目标。
- DISARM、ESTOP 和 FAULT 时定义明确策略：第一版关闭 PWM，而不是自动回中。
- 状态记录目标角、当前输出角、限幅次数和最近更新时间。

## 9. GPIO35 外部接口

- 内部 API 使用 `asserted`，避免把“GPIO 高”和“外部接口低”混淆。
- `asserted=false`：GPIO35 低，2N7002 关闭，外部接口释放。
- `asserted=true`：GPIO35 高，2N7002 导通，外部接口被拉低。
- 上电默认必须是 `false`。
- 普通断网不自动改变该接口；ESTOP 是否释放它由最终负载用途决定。
- 在用途未确认前，只有显式命令可以改变它，不能绑定到电机 ARM。

## 10. MPU6050 与传感器任务

第一版传感器链路：

1. 检查 WHO_AM_I。
2. 配置量程、DLPF 和采样率。
3. 配置 DATA_READY，并使用 GPIO8 中断通知任务。
4. ISR 只发送任务通知，不进行 I2C 访问、日志打印或浮点计算。
5. 传感器任务读取一帧数据并转换单位。
6. 更新线程安全状态快照。
7. 超时或连续 I2C 错误时执行受控的总线/设备恢复。

建议初始输出：

- 加速度：`g`。
- 角速度：`deg/s`。
- 温度：摄氏度。
- 时间戳：ESP 定时器微秒值。
- 健康字段：valid、sample_count、error_count、last_update_ms、sample_rate_hz。

接板前先实现纯函数的原始值换算和滤波测试；零偏参数用 NVS 保存，但没有真机数据前使用零默认值。

## 11. FreeRTOS 任务与并发

建议任务划分：

| 任务 | 建议周期/触发 | 职责 |
|---|---|---|
| `control_task` | 10 ms + 命令通知 | 唯一执行电机、舵机、GPIO35 的任务 |
| `sensor_task` | GPIO8 通知/超时 | 读取 MPU6050、换算并更新状态 |
| `network_task` | ESP-IDF 事件驱动 | HTTP 和连接管理，只投递命令 |
| `telemetry_task` | 100 ms | 生成状态快照、低频推送或日志 |
| `storage_task` | 低优先级、事件触发 | 保存配置/故障，不阻塞控制周期 |

并发规则：

- 驱动对象只允许其所属任务写入。
- 状态快照使用短临界区或互斥锁复制，网络发送时不长时间持锁。
- ISR 只做通知和计数。
- 禁止在控制任务里等待网络、Flash 写入或无限期 I2C 操作。
- 所有任务记录栈余量；队列、定时器和任务创建失败必须进入安全状态。

## 12. HTTP API 与协议版本

现有 API 可以继续使用，但接板前应增加版本并把改变状态的 GET 请求迁移为 POST：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/status` | 完整状态快照 |
| `POST` | `/api/v1/arm` | 解锁执行器 |
| `POST` | `/api/v1/disarm` | 安全停止并锁定 |
| `POST` | `/api/v1/estop` | 最高优先级急停 |
| `POST` | `/api/v1/fault/clear` | 清除已不存在的锁存故障 |
| `POST` | `/api/v1/drive` | throttle/steering 控制 |
| `POST` | `/api/v1/motors` | A/B 独立板测控制 |
| `POST` | `/api/v1/servo` | 舵机目标角 |
| `POST` | `/api/v1/power` | GPIO35 asserted 状态 |
| `GET` | `/api/v1/device` | 版本、构建和复位信息 |

统一响应示例：

```json
{
  "ok": true,
  "sequence": 42,
  "state": "READY",
  "error": null
}
```

错误必须区分：参数错误、当前状态禁止、硬件不可用、命令过期、队列已满和内部错误。旧的无版本 GET API 可以短期保留为兼容入口，但也必须进入同一个 `command_router`。

旧工程的六字节帧若保留，只做兼容适配。由于旧脚本对模式编号存在冲突，接板前先建立一份唯一协议表和自动化测试，不能靠注释猜测含义。

## 13. 状态与故障模型

`robot_status_t` 至少包含：

- 协议版本、固件版本、启动时间和复位原因。
- 当前状态机状态、是否 armed、是否 estop。
- Motor A/B 的目标值和实际输出值。
- 舵机目标角、实际输出角和 PWM 是否启用。
- GPIO35 asserted 状态。
- nFAULT 当前电平和锁存故障位。
- IMU 最新数据、有效性、采样率和错误计数。
- Wi-Fi 模式、连接客户端数量和最后有效控制时间。
- 命令接收、拒绝、过期、队列溢出和看门狗停车计数。
- 可用堆内存与各关键任务最小剩余栈。

建议故障位使用位掩码：

- `FAULT_DRV8833`
- `FAULT_IMU_INIT`
- `FAULT_IMU_STALE`
- `FAULT_COMMAND_TIMEOUT`
- `FAULT_QUEUE_OVERFLOW`
- `FAULT_CONFIG_INVALID`
- `FAULT_INTERNAL`

IMU 故障是否阻止手动运动应由模式决定；DRV8833 故障必须阻止电机运行。

## 14. 配置与 NVS

建立带版本号的配置结构，至少包括：

- 电机 A/B 方向反转。
- 电机斜坡、换向死区和命令超时。
- 舵机角度、脉宽、中位、方向和变化速率。
- IMU 零偏与滤波参数。
- Wi-Fi 工作模式和 STA 凭据。

加载流程：读取 -> 检查版本 -> 校验每个字段 -> 应用；任何字段非法时回到编译期安全默认值并置故障标志。不要把高频遥测写入 NVS，避免 Flash 磨损。

## 15. 无硬件测试

### 15.1 构建检查

- Debug 配置完整编译。
- Release 配置完整编译。
- 执行 `git diff --check`。
- 记录固件大小并设置增长告警。
- 编译时启用常用警告，新增代码不得引入警告。

### 15.2 纯逻辑单元测试

不依赖 GPIO 的代码应能在主机上测试：

- 电机差速混控和 `-100..100` 限幅。
- 输出斜坡和正反转过零逻辑。
- 舵机角度、脉宽和速率限制。
- MPU6050 原始值到物理单位换算。
- 状态机合法/非法转换。
- 命令过期、序列号、急停优先级和队列覆盖策略。
- NVS 配置校验与旧版本迁移。
- 六字节兼容帧和未来扩展帧的解析、坏帧恢复。

### 15.3 HTTP/上位机测试

- 对每个 API 测试正常值、边界值、缺字段、错误类型和超长输入。
- 未 ARM 时所有运动命令必须被拒绝。
- ESTOP 后普通命令不能恢复运动。
- 模拟停止发送心跳，确认软件状态进入停车/急停。
- 上位机无法连接时不崩溃、不阻塞 UI，并明确显示错误。
- 上位机退出流程必须尝试发送停止，但不能把它作为唯一安全措施。

## 16. 接板前实施顺序

1. 新增公共类型：命令、状态、故障和配置。
2. 实现安全状态机及其主机单元测试。
3. 实现 `control_manager` 和命令队列。
4. 将现有 HTTP/串口入口改为投递统一命令。
5. 完成双电机独立控制、差速混控、斜坡和换向保护。
6. 完成 nFAULT 读取、锁存和急停路径。
7. 修改舵机启动策略，增加速率限制和输出关闭。
8. 完成 MPU6050 换算、GPIO8 通知式采样和状态快照。
9. 实现版本化 API、统一响应和设备信息接口。
10. 实现配置校验、NVS 版本和安全默认值。
11. 完成主机单元测试、协议测试和上位机离线测试。
12. 完整编译并冻结第一版可烧录基线。

## 17. “接板前完成”的验收标准

满足以下条件才进入实际 PCB 烧录阶段：

- [ ] ESP-IDF Debug/Release 均可从干净构建目录成功编译。
- [ ] 启动逻辑默认不会使能电机或主动移动舵机。
- [ ] 所有运动必须经过 ARM、参数校验和状态机。
- [ ] ESTOP、DISARM、通信超时和 nFAULT 都走同一个硬件安全停止函数。
- [ ] 电机 A/B 独立控制、差速混控、斜坡和换向测试通过。
- [ ] 舵机限幅、脉宽换算和速率限制测试通过。
- [ ] 命令解析、状态机、配置校验和 IMU 换算有自动化测试。
- [ ] HTTP 与串口使用同一个内部命令模型。
- [ ] 状态接口能够说明系统为什么不能运动，而不是只返回失败。
